# 行きたい場所ストック — 設計ドキュメント

Claude Code への指示書を兼ねた設計メモ。
**このドキュメントに書かれていない機能は実装しないこと。** 判断が必要になったら、勝手に決めずに確認すること。

---

## 1. これは何か

「行きたい場所」をストックして、休日に**その中から今日行く場所を決める**ためのアプリ。

主に二人（パートナーと）で使うことを想定する。将来的には一般公開し、アフィリエイトによる収益化も視野に入れる。

## 2. 解く課題

土曜の朝、二人とも予定がなく「今日どこ行く?」「どこでもいいよ」で決まらない状態を解消する。

## 3. 競合と差別化

本当の競合は Google マップの「保存」リスト。地図・共有・営業時間はすべて向こうが上なので、そこでは戦わない。

Google マップの保存リストの欠陥は **溜まる一方で腐ること**。50件を超えると開かなくなり、半年後には「なぜ保存したか」を思い出せない。

したがってこのアプリが注力するのは次の2点のみ。

- **決める** — ストックの中から今日の候補を提示する
- **消化する** — 行ったらストックから減る。残数が見える

想定ユーザーは **休日の行き先をひとりでは決めない人たち**。カップル、友人同士、家族のいずれでも成立する。

地域や移動手段は問わない。エリアタグは移動手段に依存しない仕組みのため、都心の電車移動でも郊外の車移動でも同じように使える。

このペルソナは実際に設計へ効いている。`wishes` を `places` から分けているのも、行きたい度のスコアを持つのも、招待の仕組みを段階4に置いているのも、複数人で決めることを前提としているため。一人で使うだけなら `wishes` は不要になる。

---

## 4. やらないこと（重要）

以下は検討した上で**意図的に捨てた**。実装しないこと。良かれと思って足さないこと。

| 項目 | 理由 |
|---|---|
| 外部 API の利用（地図・ジオコーディング・天気） | 課金リスクと規約の縛りを避けるため。依存ゼロで作る |
| 緯度経度の保存 | エリアタグで代替する |
| 距離・所要時間の計算 | 一切計算しない。主観ラベルのみ |
| ユーザーの所在地・現在地の取得 | 持たない |
| 地図表示 | 作らない |
| 経路案内 | Google マップの検索 URL に文字列を渡して終わり |
| 屋内 / 屋外の区別、天気連携 | 不要と判断した |
| 営業時間、「今から行けるか」 | 外部 API なしでは取得できない。諦める |
| 共有メニューからの登録（Web Share Target） | 後回し。まず通常のフォームだけ |
| 引き直し回数の制限 | 山札方式で自然に収束させる |

## 5. 用語

- **ストック** — 登録済みで未訪問の場所の集合
- **一言** — その場所を登録した理由。必須。半年後の自分が思い出せる文
- **エリアタグ** — 「箱根・小田原」のような地名のまとまり。1つの場所に1つだけ
- **帯（band）** — エリアタグが持つ主観的な遠さ。`near` / `day` / `far` の3値
- **行きたい度** — 各ユーザーが場所ごとに付けるスコア
- **山札** — その日すでに提案に出した場所の集合。同じ日には再提示しない
- **消化** — 訪問記録を付けてストックから外すこと

---

## 6. データモデル

DB は PostgreSQL。

### users
最初から置く。収益化時に課金の主体を特定できる必要があるため、後付けは不可。

- `email`
- `name`

### areas
エリアタグ。ユーザーが自分の生活圏に合わせて作る。

- `name` — 表示名（例: 箱根・小田原）
- `band` — enum: `near` / `day` / `far`

`band` の意味づけはユーザーの主観であり、システムは分数や距離を保持しない。
UI に「30分以内」などの時間表記を出さないこと。計算していると誤解させるため。

### places
- `area_id` — 必須。1件につき1つ
- `name` — 店名・施設名。ユーザーが手入力
- `note` — 一言。**必須**
- `created_at` — 塩漬け判定に使う

### wishes
誰がどれくらい行きたいか。places とは必ず分ける。同一テーブルに `riki_score` のような人別カラムを作らないこと。人数が増えた時点で破綻する。

- `place_id`
- `user_id`
- `score` — 整数

### visits
- `place_id`
- `visited_on`
- `want_again` — boolean

`visits` が存在する place はストックから外れる（消化済み）。

## 7. 画面と挙動

### 7-1. 登録

入力項目は3つだけ。

1. 店名（手入力）
2. 一言（必須）
3. エリアタグ（既存からサジェスト、なければ新規作成。新規作成時は帯も選ぶ）

外部 API は呼ばない。オートコンプリートは存在しない。

同じ場所の重複登録を機械的に防ぐ手段はない（一意な識別子を持たないため）。入力中に既存の place を部分一致で表示する程度で足りる。

### 7-2. 一覧

ストック（未訪問）の一覧。エリアタグでの絞り込みができる。

### 7-3. 今日決める（製品の核）

開いた時点で**すでに3件表示されている**。ユーザーに条件を入力させない。

- 帯の絞り込みは「近場 / 日帰り / 遠出」の3ボタン。デフォルトは全件
- 各カードに表示するのは、店名 / 一言 / エリアタグ / 登録からの経過期間
- 一言は店名より目立つ位置に置く。判断材料はそこにあるため
- 行きたい度は**合計のみ**を表示する（暫定。9節参照）

**アクション**

- `別の3件` — 山札から次の3件を引く。回数制限なし
- `これにする` — Google マップの検索 URL を開く。同時に訪問記録の入力へ誘導する

**候補が尽きたとき**

「今日はもう候補がありません」と表示する。これは失敗表示ではなく、「今日は家にいよう」という結論を提示する画面として扱う。登録画面への導線をここに置く。

### 7-4. 訪問記録

訪問日と「また行きたいか」を記録する。記録するとストックから消える。

## 8. 提案ロジック

### 3件の内訳

| 枠 | 選び方 |
|---|---|
| 2件 | 行きたい度の合計が上位層の中からランダム |
| 1件 | **スコアは高いのに古いもの**（塩漬け）からランダム |

塩漬け枠を「最も古いもの」にしないこと。古いまま残っているのはスコアが低いからである場合が多く、そのまま出すと「二人とも行きたくない場所」が毎日1枠を占領してノイズになる。

該当が0件の場合は、その枠も上位層から埋める。

### 山札

- その日すでに提案に出した `place_id` を保持し、同じ日には再提示しない
- 状態はセッションで保持する。DB に保存する必要はない
- 日付が変わったらリセットする

### 除外

- 訪問済み（`visits` がある）place は候補に含めない

## 9. まだ決まっていないこと

**勝手に決めずに確認すること。** 以下はすべて後から変更可能なため、暫定値で進めてよいが、独自に仕様を拡張しないこと。

- **グループの扱い** — 二人で共有する仕組みは段階4で実装する。ただし `places` / `areas` を後から user 単位からグループ単位に移すのは手戻りが大きいので、最初から `group`（世帯）を置いて1人グループとして始める案を検討中
- **店名と一言を分けるか統合するか** — 暫定で分ける
- **行きたい度のスケール** — 3段階か5段階か未定
- **スコアの内訳を見せるか** — 暫定で合計のみ。内訳を出すと点数の低い側が気を使う懸念があるため
- **山札を二人で共有するか、各自で引くか** — 未決
- **「今日の気分」チップの導入** — 保留。エリア絞り込みだけで物足りなければ後から足す
- **認証方式** — `users` を置くことのみ確定
- **収益化の置き場所** — アフィリエイトを想定しているが未設計

## 11. 実装の順序

期間では区切らない。状態で区切る。

1. **土台** — `users` / `places` / `areas`、登録フォーム、一覧。**この段階の途中で一度デプロイを通しておくこと**（最後に回すと環境周りの問題が一気に出る）
2. **決める** — 提案3件、山札、帯での絞り込み
3. **消化** — `visits`、ストックから消える挙動
4. **二人で使う** — 招待、`wishes` のスコア
5. **公開** — サインアップ、規約、プライバシーポリシー、アフィリエイト

段階1が終わったら、以降の実装と並行して**実際に自分でストックを溜め始める**。20件程度ないと段階2の動作を確認できない。

## 12. 判断の背景

実装中に「なぜこうなっているのか」が気になったとき用のメモ。

- **なぜ外部 API を使わないのか** — Google Places は従量課金で、請求額の上限による自動停止がない。また取得した緯度経度は30日を超えて保存できず、表示名・住所・評価などは保存自体が認められていない。収益化前にコストと規約リスクだけが積み上がる構造を避けた
- **なぜ名前を手入力させるのか** — 上記の制約を外した結果、名前は自由に保存できるようになった。オートコンプリートがない分だけ入力の手間は増えるが、どのみち一言は入力するため許容範囲と判断した
- **なぜ距離を計算しないのか** — 同じ場所でも高速代・渋滞・出発時刻で体感は変わる。計算値より「自分が日帰り圏と感じているか」のほうが休日の判断に役立つ
- **なぜ引き直しに制限を設けないのか** — 制限は「なぜ3回までなのか」を説明できず不信感を生む。山札方式なら引くほど候補が減るという納得できる理屈で自然に収束する
- **なぜ提案型なのか** — 条件を入力させる形式は、入力が面倒で使われなくなる。開いた瞬間に答えが出ている状態を優先した
