# 行きたい場所 — 設計ドキュメント

Claude Code への指示書を兼ねた設計メモ。
**このドキュメントに書かれていない機能は実装しないこと。** 判断が必要になったら、勝手に決めずに確認すること。

---

## 1. これは何か

「行きたい場所」を溜めておき、休日に**その中から今日行く場所を決める**ためのアプリ。

主に二人（パートナーと）で使うことを想定する。将来的には一般公開し、アフィリエイトによる収益化も視野に入れる。

## 2. 解く課題

土曜の朝、二人とも予定がなく「今日どこ行く?」「どこでもいいよ」で決まらない状態を解消する。

## 3. 競合と差別化

本当の競合は Google マップの「保存」リスト。地図・共有・営業時間はすべて向こうが上なので、そこでは戦わない。

Google マップの保存リストの欠陥は **溜まる一方で腐ること**。50件を超えると開かなくなり、半年後には「なぜ保存したか」を思い出せない。

したがってこのアプリが注力するのは次の2点のみ。

- **決める** — 行きたい場所の中から今日の候補を提示する
- **消化する** — 行ったら行きたい場所から外れる。残数が見える

想定ユーザーは **休日の行き先をひとりでは決めない人たち**。カップル、友人同士、家族のいずれでも成立する。

地域や移動手段は問わない。距離感は主観ラベルであり移動手段に依存しないため、都心の電車移動でも郊外の車移動でも同じように使える。

このペルソナは実際に設計へ効いている。`wishes` を `places` から分けているのも、行きたい度のスコアを持つのも、招待の仕組みを段階4に置いているのも、複数人で決めることを前提としているため。一人で使うだけなら `wishes` は不要になる。

---

## 4. やらないこと（重要）

以下は検討した上で**意図的に捨てた**。実装しないこと。良かれと思って足さないこと。

| 項目 | 理由 |
|---|---|
| 外部 API の利用（地図・ジオコーディング・天気） | 課金リスクと規約の縛りを避けるため。依存ゼロで作る |
| 緯度経度の保存 | 距離感（主観ラベル）で代替する |
| 距離・所要時間の計算 | 一切計算しない。主観ラベルのみ |
| ユーザーの所在地・現在地の取得 | 持たない |
| 地図表示 | 作らない |
| 経路案内 | Google マップの検索 URL に文字列を渡して終わり |
| 屋内 / 屋外の区別、天気連携 | 不要と判断した |
| 営業時間、「今から行けるか」 | 外部 API なしでは取得できない。諦める |
| 共有メニューからの登録（Web Share Target） | 後回し。まず通常のフォームだけ |
| 引き直し回数の制限 | 山札方式で自然に収束させる |

## 5. 用語

- **行きたい場所** — 登録済みで未訪問の場所の集合（「また行きたい：はい」で記録した訪問済みの場所も含む）
- **一言** — その場所を登録した理由。必須。半年後の自分が思い出せる文
- **距離感** — 場所が持つ主観的な遠さ。`near`（近場） / `day_trip`（日帰り） / `far`（遠出）の3値
- **行きたい度** — 各ユーザーが場所ごとに付けるスコア
- **山札** — その日「別の3件」で見送った場所の集合。同じ日には再提示しない
- **消化** — 「また行きたい：いいえ」で訪問記録を付けて行きたい場所から外すこと

## 6. データモデル

DB は PostgreSQL。

### users
最初から置く。収益化時に課金の主体を特定できる必要があるため、後付けは不可。

- `email`
- `name`

`users` には `group_id` を持たせない。所属は `memberships` で表す。

### groups
世帯。`places` の所有者はユーザーではなくグループとする。二人で共有する仕組み（段階4）に備え、最初からグループ単位でデータを持つ。

- 属性なし（`id` とタイムスタンプのみ）

サインアップ時に、そのユーザーだけが所属する1人グループを自動で作成する。二人で共有する仕組み（招待）は段階4で実装する。

### memberships
users と groups の中間テーブル。

- `user_id` — 必須
- `group_id` — 必須

`(user_id, group_id)` の組み合わせは一意。現状は1人1グループの前提で運用する。

### places
- `group_id` — 必須。所有するグループ
- `name` — 場所の名前（店・施設のほか、海や山などの屋外スポットも含む）。ユーザーが手入力。必須。最大100文字
- `note` — 一言。**必須**。最大200文字
- `distance` — 距離感。必須。enum: `near`（近場） / `day_trip`（日帰り） / `far`（遠出）。DB には文字列（`"near"` など）で保存する
- `created_at` — 塩漬け判定に使う

`distance` は数値ではなく主観ラベルであり、意味づけはユーザーの主観に任せる。システムは分数や距離を保持しない。
UI に「30分以内」「10km」などの時間・距離の数値表記を出さないこと。計算していると誤解させるため。

### wishes
誰がどれくらい行きたいか。places とは必ず分ける。同一テーブルに `riki_score` のような人別カラムを作らないこと。人数が増えた時点で破綻する。

- `place_id`
- `user_id`
- `score` — 整数

### visits
- `place_id` — 必須。記録した場所
- `visited_on` — 訪問日。必須。今日（日本時間）以前の日付
- `want_again` — また行きたいか。boolean。必須（未選択はエラー）

`want_again` が false の visits がある place は行きたい場所から外れる（消化済み）。true の記録しかない place は行きたい場所に残る。
1つの place に visits は何件でも付けられる。place を削除すると、その place の visits も消える。

## 7. 画面と挙動

### ナビバー

ログイン中は、画面上部のナビバーに次のメニューを並べる。

```
今日どこ行く？ ｜ 行きたい場所 ｜ 訪問記録 ｜ （ユーザー名） ▼
                                           ├ アカウント設定
                                           └ ログアウト
```

- 「今日どこ行く？」は今日決める（7-3）、「行きたい場所」は一覧（7-2）、「訪問記録」は訪問記録の一覧（7-4）を開く
- ユーザー名を押すとドロップダウンが開き、「アカウント設定」と「ログアウト」を選べる。ドロップダウンはナビバーに合わせて暗い配色にする
- 「アカウント設定」は名前・メールアドレス・パスワードの変更とアカウント削除の画面を開く。画面の見出しとタブのタイトルも「アカウント設定」にする
- スマホ幅ではメニューをハンバーガーメニューに畳む。ドロップダウンはその中で縦に開く
- 未ログイン時は「ログイン」「新規登録」だけを置く

### 7-1. 登録

入力項目は3つだけ。

1. 場所の名前（手入力）
2. 一言（必須）
3. 距離感（近場 / 日帰り / 遠出 から選ぶ。初期値なし）

外部 API は呼ばない。オートコンプリートは存在しない。

同じ場所の重複登録を機械的に防ぐ手段はない（一意な識別子を持たないため）。入力中に既存の place を部分一致で表示するヒントは、初期リリースでは見送る。

登録に成功したら完了メッセージを出し、空のフォームに戻る（続けて登録できるようにするため）。

### 7-2. 一覧

行きたい場所（消化済みでない場所）の一覧で、画面名は「行きたい場所」。自分のグループの場所を**登録が新しい順**に並べる。

- 各行に表示するのは、場所の名前 / 一言 / 距離感。時間・距離の数値表記は出さない（6節）
- 上部の「すべて / 近場 / 日帰り / 遠出」のボタンで距離感ごとに絞り込む。デフォルトは「すべて」。選択中のボタンは塗りつぶしで示す
- 絞り込みは URL のクエリ（例: `/places?q[distance_eq]=near`）で行う。並び順は URL から変えられず、常に新しい順
- 各行に「訪問を記録」リンクを置き、訪問の記録画面（7-4）を開く。見た目は「編集」リンクと同じ

**0件のとき**

場所が0件になる理由（登録なし・すべて消化・絞り込んだ結果だけ0件・距離感に不正な値が指定された）によらず、一律で「場所がありません」と表示し、登録画面への導線を置く。不正な値（例: `q[distance_eq]=xxx`）でもエラーにはしない。

- 行きたい場所が1件もない（すべて消化済みも含む）：絞り込みボタンと見出し横の登録ボタンは出さず、案内文と登録リンクだけにする
- 行きたい場所はあるが絞り込んだ結果だけ0件：ほかの距離感に切り替えられるよう、絞り込みボタンは表示したままにする

### 7-3. 今日決める（製品の核）

開いた時点で**すでに3件表示されている**。ユーザーに条件を入力させない。

- 距離感の絞り込みは「近場 / 日帰り / 遠出」の3ボタン。デフォルトは全件
- 各カードに表示するのは、場所の名前 / 一言 / 距離感 / 登録からの経過期間
- 場所の名前を大きく目立たせ、一言はその下に通常の大きさで置く
- 行きたい度は**合計のみ**を表示する（暫定。9節参照）
- 候補が3件未満なら、ある分だけ表示する
- 山札（8章）は1日1つで、距離感を切り替えても共通。日本時間で日付が変わったらリセットする
- 山札が減るのは `別の3件` を押したときだけ。押した時点で表示中の3件を見送り、次の3件を引く
- 再読み込みでは同じ3件を表示し、山札は減らさない
- 手札（表示中の3件）は距離感ごとに覚える。距離感を切り替えても山札は減らず、元の距離感に戻ると同じ3件を表示する
- 他の距離感で見送った場所は手札から外し、補充はしない。手札が0件になったら新しく3件を引く
- 引き切ったあとに新しく登録した場所は、再読み込みで表示する

**アクション**

- `別の3件` — 表示中の3件を見送り、まだ見送っていない場所から次の3件を引く。回数制限なし
- `これにする` — Google マップの検索 URL を開く

**候補が尽きたとき**

場所が0件になる理由（登録なし・すべて消化・今日の候補を引き切った・選んだ距離感に場所がない）によらず、一律で「場所がありません」と表示する。登録画面への導線をここに置く。

### 7-4. 訪問記録

行った場所に、訪問日と「また行きたいか」を記録する。「また行きたいか」が行きたい場所から外す分かれ目になる。

**入口**

- 一覧（7-2）の各行の「訪問を記録」リンクから記録画面を開く。今日決める画面（7-3）からは誘導しない
- 記録画面には対象の場所の名前と、行きたい場所に戻るリンクを置く

**入力項目**

1. 訪問日 — 初期値は今日（日本時間）。明日以降の日付はエラーにする
2. また行きたいか — 「はい / いいえ」から選ぶ。初期値なし。必須

入力エラーのときは、入力値（選んだ「はい / いいえ」を含む）を残したまま記録画面を再表示する。

**はい / いいえの違い**

- いいえ：消化済みになり、行きたい場所と今日決めるから外れる。「○○を訪問済みにしました」と表示して行きたい場所に戻る
- はい：行きたい場所に残り、今日決めるにも出る。次に行ったらまた記録できる（1つの場所に何件でも記録できる）。「○○の訪問を記録しました（行きたい場所に残ります）」と表示して行きたい場所に戻る

**訪問記録の一覧**

画面名は「訪問記録」（ナビバーの「訪問記録」から開く）。

- 自分のグループの訪問記録を**訪問日の新しい順**に並べる（同じ訪問日なら、あとに記録したものが上）
- 各行に表示するのは、場所の名前 / 一言 / 距離感 / 訪問日 / また行きたいか（はい / いいえ）
- 0件のときは「まだ訪問した場所はありません」と表示する

**取り消し**

- 訪問記録の一覧の各行に「取り消す」ボタンを置く。押すと確認ダイアログを出し、OK で訪問記録を消す
- 取り消したら「○○の訪問記録を取り消しました」と表示して訪問記録の一覧に戻る
- 「いいえ」の記録を取り消すと、その場所は行きたい場所に戻る（ほかに「いいえ」の記録がなければ）

**権限**

自分のグループの場所にだけ記録・取り消しができる。他のグループの場所の id を直接指定した場合、記録画面の表示・記録はできず、見つからない扱い（404）にする。他のグループの記録の id を直接指定した場合も、取り消しはできず、見つからない扱いにする（「10. 技術方針」の認可エラーの方針を参照）。消化済みの場所の記録画面・記録も、自分のグループかどうかによらず見つからない扱いにする。

### 7-5. 編集・削除

登録した場所を直したり、片付けたりする。

**編集**

- 一覧（7-2）の各行の「編集」リンクから編集画面を開く。編集画面には行きたい場所に戻るリンクを置く
- 入力項目とバリデーションは登録（7-1）と同じ3つ（場所の名前 / 一言 / 距離感）。フォームは登録画面と共通
- 開いた時点で今の値が入っている
- 更新に成功したら「○○を更新しました」と表示して行きたい場所に戻る（絞り込みは解除される）
- 入力エラーのときは、入力値を残したまま編集画面を再表示する

**削除**

- 編集画面の下に「削除する」ボタンを置く。一覧から直接は消せない
- 押すと確認ダイアログを出し、OK で DB から完全に消す（論理削除・ゴミ箱・取り消しはない）
- 削除したら「○○を削除しました」と表示して行きたい場所に戻る

**削除と消化（7-4）の違い**

- 削除：**行かずにやめた場所**を消す。閉店した、興味がなくなった、二重に登録した、など。記録は何も残らない
- 消化：**行った場所（また行きたくない）**を行きたい場所から外す。訪問記録（visits）として残る。「また行きたい：はい」で記録した場所は行きたい場所に残る

**権限**

自分のグループの場所だけを編集・削除できる。他のグループの場所の id を直接指定しても、表示・更新・削除はできない（見つからない扱いにする）。

## 8. 提案ロジック

### 3件の内訳

| 枠 | 選び方 |
|---|---|
| 2件 | 行きたい度の合計が上位層の中からランダム |
| 1件 | **スコアは高いのに古いもの**（塩漬け）からランダム |

> 段階2（11章）では行きたい度がまだないため、暫定で全件からランダムに3件を選ぶ。行きたい度を使う選び方（上位層・塩漬け枠）は段階4で入れる。

塩漬け枠を「最も古いもの」にしないこと。古いまま残っているのはスコアが低いからである場合が多く、そのまま出すと「二人とも行きたくない場所」が毎日1枠を占領してノイズになる。

該当が0件の場合は、その枠も上位層から埋める。

### 山札

- その日「別の3件」で見送った `place_id` を保持し、同じ日には再提示しない
- 状態はセッションで保持する。DB に保存する必要はない
- 日付が変わったらリセットする

### 除外

- 消化済み（`want_again` が false の visits がある）place は候補に含めない
- 「また行きたい」（`want_again` が true の visits しかない）place は候補に含める

## 9. まだ決まっていないこと

**勝手に決めずに確認すること。** 以下はすべて後から変更可能なため、暫定値で進めてよいが、独自に仕様を拡張しないこと。

- **招待承諾時の元グループの扱い** — 案1：空なら削除／案2：データを引っ越して削除／案3：残して複数所属。段階4の招待機能の設計時に決める
- **退会時にメンバーが0人になったグループの扱い** — 現状は退会（ユーザー削除）時に `memberships` だけが消え、`groups` の行は残る。どう扱うかは #39 で決める
- **場所の名前と一言を分けるか統合するか** — 暫定で分ける
- **行きたい度のスケール** — 3段階か5段階か未定
- **スコアの内訳を見せるか** — 暫定で合計のみ。内訳を出すと点数の低い側が気を使う懸念があるため
- **山札を二人で共有するか、各自で引くか** — 未決
- **また行きたい場所を再び候補に出すまでの間隔** — 今は記録した当日から候補に出る（「はい」で記録した場所は、表示中の手札にも残る）。行ったばかりの場所をしばらく出さないかは未決
- **「今日の気分」チップの導入** — 保留。距離感の絞り込みだけで物足りなければ後から足す
- **収益化の置き場所** — アフィリエイトを想定しているが未設計

## 10. 技術方針

- Ruby on Rails。フロントエンドも Rails で作る（Haml + Hotwire）
- DB は PostgreSQL
- 認証は Devise を使う
- 一覧の絞り込みは ransack を使う。URL から検索できる項目はモデルの許可リスト（`ransackable_attributes` など）で絞る
- 他のグループのデータへのアクセスは Pundit の `authorize` で拒否し、`ActiveRecord::RecordNotFound`（見つからない）として扱う。本番環境では存在しない ID を指定したときと同じ `public/404.html` を 404 Not Found で返す。flash は出さない
  - 理由: 他のグループのデータが存在するかどうかを推測できないようにするため。認可エラーを存在しない ID と同じ処理に通すことで、どの環境でも両者は同じ扱いになる
  - development / test では、存在しない ID と同じく詳細なエラー画面（デバッグ画面）になる。元の `Pundit::NotAuthorizedError` は原因（cause）として表示されるため、開発中は認可で拒否されたことを確認できる
  - 未ログイン時は Devise がログイン画面へリダイレクトする（認証の範囲のため、この方針の対象外）
- 外部 API への依存はゼロ
- 秘密情報は `RAILS_MASTER_KEY` のみ。リポジトリにはコミットせず、Render の環境変数で管理する（`DATABASE_URL` は Render が DB から自動で設定する）
- ホスティングは Render（Web + Postgres）。手順は [docs/deploy.md](../deploy.md)

## 11. 実装の順序

期間では区切らない。状態で区切る。

1. **土台** — `users` / `places`、登録フォーム、一覧。**この段階の途中で一度デプロイを通しておくこと**（最後に回すと環境周りの問題が一気に出る）
2. **決める** — 提案3件、山札、距離感での絞り込み
3. **消化** — `visits`、行きたい場所から外れる挙動
4. **二人で使う** — 招待、`wishes` のスコア
5. **公開** — サインアップ、規約、プライバシーポリシー、アフィリエイト

段階1が終わったら、以降の実装と並行して**実際に自分で行きたい場所を溜め始める**。20件程度ないと段階2の動作を確認できない。

## 12. 判断の背景

実装中に「なぜこうなっているのか」が気になったとき用のメモ。

- **なぜ外部 API を使わないのか** — Google Places は従量課金で、請求額の上限による自動停止がない。また取得した緯度経度は30日を超えて保存できず、表示名・住所・評価などは保存自体が認められていない。収益化前にコストと規約リスクだけが積み上がる構造を避けた
- **なぜ名前を手入力させるのか** — 上記の制約を外した結果、名前は自由に保存できるようになった。オートコンプリートがない分だけ入力の手間は増えるが、どのみち一言は入力するため許容範囲と判断した
- **なぜ距離を計算しないのか** — 同じ場所でも高速代・渋滞・出発時刻で体感は変わる。計算値より「自分が日帰り圏と感じているか」のほうが休日の判断に役立つ
- **なぜ引き直しに制限を設けないのか** — 制限は「なぜ3回までなのか」を説明できず不信感を生む。山札方式なら `別の3件` で見送るほど候補が減るという納得できる理屈で自然に収束する
- **なぜ提案型なのか** — 条件を入力させる形式は、入力が面倒で使われなくなる。開いた瞬間に答えが出ている状態を優先した
